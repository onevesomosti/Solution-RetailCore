> Назначение документа: безопасно включить Order State Read Model как источник чтения состояния и истории заказа для ограниченного пилотного сценария, сохранив Oracle/legacy-контур как источник истины и fallback.

## 1. Цель переключения

> Цель переключения --- перевести чтение состояния и истории заказа для ограниченного пилотного сценария с текущего восстановления данных из legacy-контура на Order State Read Model. После переключения поддержка должна получать согласованное текущее состояние, историю и причины отклонений. Oracle остаётся операционным источником истины и источником для сверки. Численные пороги допустимых расхождений в источниках отсутствуют и должны быть согласованы до запуска.

## 2. Объём переключения

### 2.1. Включаем

- чтение текущего состояния пилотных заказов из Order State Read Model
- отображение истории канонических событий для поддержки
- сравнение Read Model с Oracle/legacy-состоянием
- мониторинг расхождений, ошибок и дублей

### 2.2. Не включаем

- запись состояния заказа через Read Model
- Core Order Create, Pricing & Promo, Payment Orchestration и Delivery Routing
- отключение Oracle
- переключение всех потребителей
- изменение логистических и платёжных интеграций

### 2.3. Критерии успешного переключения

| Критерий | Целевое значение | Где проверяем | Кто подтверждает |
|---|---:|---|---|
| Необъяснимые расхождения состояний| TBD | Сверка Oracle с Read Store | Команда заказов и техлид |
| Потерянные данные /дублированные | TBD | Event monitoring | Техлид |
| Поддержка может восстановить историю заказа | Подтверждено на сценариях | Admin/Support tools | Руководитель поддержки |

## 3. Условия запуска: go / no-go

| Условие | Тип | Как проверяем | Порог / ожидаемое состояние | Статус | Ответственный |
|---|---|---|---|---|---|
| Event Bus и Read Model развернуты | Техническое | Health checks / тестовыйпоток | Все компоненты доступны | go | Техлид |
| История заказов подготовлена | Данные | Сверка Oracle / Read Store | TBD | go | DBA |
| Существует сorrelation ID и event ID | Наблюдаемость | Логи | Заказ прослеживается end-to-end | go | SRE |
| Дашборды и аллерты готовы | Наблюдаемость | Проверка сигналов | Все критичные сигналы наблюдаемы | go | SRE |
| Legacy-чтение доступно как fallback| Техническое | Тест возврата | Возврат проверен | go | Команда разработки |
| Инструкция для поддержки готова | Операционное | Dry run | Поддержка понимает новый источник| go | Руководитель поддержки |
| Назначен человек с правом на rollback | Организационное | Проверка | Назначение зафиксировано | go | Бизнес-владелец |

При отсутствии согласованных численных порогов или ответственного за go/no-go запуск - `no-go`.

## 7. Пошаговый сценарий переключения

| Шаг | Время / окно | Действие | Ответственный | Проверка результата | Решение при ошибке |
|---:|---|---|---|---|---|
|   1 | T-60 | Зафиксировать начало окна и участников  | Руководитель переключения | Все роли на связи  | No-go |
|   2 | T-45 | Проверить Event Bus, Read Model, Read Store и monitoring | Техлид + SRE | Health checks и дашборды в норме  | No-go |
|   3 | T-30 | Выполнить контрольную сверку пилотных заказов | Data/DBA | Расхождения в согласованном пороге  | No-go  |
|   4 | T-15  | Проверить fallback на legacy-чтение | Backend  | Возврат работает  | No-go |
|   5 | T0 | Включить Read Model для ограниченного пилотного сегмента | Backend | Запросы пилота идут в новый read-контур | Rollback при ошибке |
|   6 | T+15 | Сверить состояния, lag, ошибки и историю | SRE + Data + поддержка | Пороговые критерии соблюдены | Не расширять / rollback |
|   7 | T+30| Проверить реальные сценарии поддержки  | Поддержка  | Состояние и история объяснимы | Вернуть legacy-чтение |
|   8 | T+60 | Принять решение о сохранении пилота | Руководитель переключения + бизнес-владелец | Критерии успешности выполнены | Rollback / продлить наблюдение |

*Относительные интервалы — рабочая структура runbook, а не подтверждённые требования RetailCore. Точное окно утверждается перед запуском.

### 10.2. Шаги rollback

| Шаг | Действие | Ответственный | Проверка результата | Что делать с данными, созданными в новом контуре |
|---:|---|---|---|---|
|   1 | Остановить расширение пилота | Руководитель переключения | Новые consumers не подключаются | Сохранить данные для анализа |
|   2 | Переключить пилотное чтение обратно на legacy | Backend | Поддержка снова читает старый источник | Read Store не удалять |
|   3 | При необходимости приостановить consumers Read Model | Backend/SRE | Нет неконтролируемой обработки | События сохранить для повторной обработки  |
|   4 | Зафиксировать диапазон спорных заказов/events| Data/DBA | Список сформирован | Выполнить reconciliation  |
|   5 | Уведомить поддержку, ИТ и бизнес | Руководитель переключения | Все участники знают режим работы | Спорные случаи обрабатываются через legacy |

### 10.3. Состояние после rollback

| Область | Ожидаемое состояние после отката | Как проверяем |
|---|---|---|
| Чтение  | Пилот снова использует legacy | Проверка маршрутизации |
| Данные | Oracle остаётся источником истины. Read Store сохранён для анализа | Сверка |
| Очереди / события | События не потеряны и не переобрабатываются неконтролируемо | Мониторинг |
| Статусы | Поддержка видит объяснимое legacy-состояние | Контрольные заказы|
| Поддержка | Использует прежнюю инструкцию | Подтверждение руководителя поддержки |
