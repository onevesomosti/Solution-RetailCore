## 1. Краткое резюме roadmap

> Миграция выполняется инкрементально, потому что RetailCore критична для бизнеса, а order flow сильно связан с Java-монолитом и Oracle. Сначала команда фиксирует базовые метрики, потребителей данных, модель состояний и канонические события. Затем запускается пилот Order Event Bus и Order State Read Model без переноса записи из монолита. После стабилизации read-контура выбранные интеграции постепенно переводятся через Integration Layer/ACL. Аналитическое чтение переводится на события и Analytics Store после появления устойчивого событийного потока. Order Create, Payment Orchestration, основной Delivery Routing и Oracle остаются в легаси-контуре на этом горизонте. Основные риски — расхождение состояний, потеря/дубли событий, дубли у партнёров и неполный реестр потребителей Oracle.

## 2. Стартовое и целевое состояние

| Состояние | Описание | Ключевые ограничения | Метрики / признаки состояния |
|---|---|---|---|
| AS-IS | Монолит оркестрирует checkout. Oracle хранит операционные данные и часть логики. Интеграции неоднородны, аналитика частично читает Oracle напрямую | Высокая связаность, скрытые потребители, ручные исключения | Базовые значения метрик TBD |
| Промежуточное состояние 1 | Канонические события публикуются, Read Model работает параллельно старому контуру | Oracle остаётся источником истины | Сверка Oracle / Read Model, потерянные/дублированные события |
| Промежуточное состояние 2 | Read Model стабилен, выбранные интеграции проходят через ACL, легси-пути сохранены | Основной Delivery Routing остаётся в монолите | Дубли, расхождения статусов, ручные разборы |
| TO-BE первого этапа | Событийный/read-контур стабилен, часть интеграций изолирована, новые аналитические потребители используют Analytics Store | order flow и Oracle не декомпозированы | Метрики не ухудшены, согласованные пороги достигнуты |

## 3. Принципы построения roadmap

- **Сначала измеряем, потом меняем:** фиксируем расхождения состояний, ручные разборы, дубли интеграций, нагрузку аналитики на Oracle и время восстановления истории заказа.
- **Сначала изолируем риск, потом расширяем сценарий:** новый read-контур не становится владельцем записи на первом этапе.
- **Сначала управляемый пилот, потом масштабирование:** сегмент пилота и численные пороги должны быть согласованы до cutover.
- **Сначала модель состояний, потом потребители:** канонические события и маппинг легаси-статусов определяются до переключения Read Model, ACL и аналитики.
- **Сначала реестр потребителей данных, потом декомпозиция:** скрытые потребители Oracle выявляются до сокращения прямого чтения.

## 5. Детализация этапов

### Этап 0. Подготовка и измерение

| Раздел | Содержание |
|---|---|
| Цель этапа | Получить проверяемую базовую линию и условия безопасного пилота |
| Какие точки трансформации закрывает | Подготавливает все три точки |
| Что меняется в процессе | Появляются единые правила измерения и go/no-go |
| Что меняется в архитектуре | Рабочий трафик не переключается |
| Что не меняется | Checkout, payment, routing, Oracle |
| Входные условия | Доступ к логам, данным и владельцам систем |
| Выходные условия | Event schema, маппинг статусов, correlation ID, реестр потребителей и пороги согласованы |
| Метрики этапа | Базовые значения всех метрик трансформации |
| Риски этапа | Неполные источники и скрытые потребители |
| Условие остановки | Базовую линию или критичные зависимости подтвердить невозможно |

### Этап 1. Пилот событий и Read Model

| Раздел | Содержание |
|---|---|
| Цель этапа | Проверить канонические события и новое представление состояния без переноса записи |
| Какие точки трансформации закрывает | Канонические события заказа и Order State Read Model |
| Что меняется в процессе | Поддержка получает возможность сверять новое представление со старым |
| Что меняется в архитектуре | Order Event Bus, Read Model, Read Store |
| Что не меняется | Oracle остаётся источником истины, core order flow остаётся в монолите |
| Входные условия | Завершён этап 0, мониторинг и rollback готовы |
| Выходные условия | Новый read-контур воспроизводит согласованное состояние и историю |
| Метрики этапа | Расхождения состояний, потери/дубли событий время восстановления истории |
| Риски этапа | Потери, дубли, неверный порядок событий, устаревание Read Model |
| Условие остановки | Необъяснимое расхождение с операционным состоянием или потеря бизнес-события |

### Этап 2. Стабилизация интеграций через ACL

| Раздел | Содержание |
|---|---|
| Цель этапа | Снизить неоднородность интеграций без переноса Delivery Routing |
| Какие точки трансформации закрывает | Integration Layer / ACL |
| Что меняется в процессе | Выбранные партнёрские сценарии идут через ACL |
| Что меняется в архитектуре | ACL адаптирует легаси-контракты и публикует статусы/события |
| Что не меняется | Routing-решения остаются в монолите, немигрированные партнёры используют легаси |
| Входные условия | Стабильный событийный контур, выбран пилотный партнёр/сценарий |
| Выходные условия | Пилотная интеграция стабильна и имеет проверенный fallback |
| Метрики этапа | Дубли, retry, потерянные подтверждения, ручные исправления |
| Риски этапа | Двойная отправка, потеря подтверждения, расхождение статусов |
| Условие остановки | ACL создаёт дубли, теряет подтверждения или нарушает согласованность статусов   |

### Этап 3. Аналитическое чтение и расширение

| Раздел | Содержание |
|---|---|
| Цель этапа | Снизить зависимость новых аналитических потребителей от операционной Oracle |

| Что меняется в процессе | Новые/мигрируемые витрины читают Analytics Store |
| Что меняется в архитектуре | Analytics Ingestion и Analytics Store |
| Что не меняется | Legacy-отчёты могут временно читать Oracle |
| Входные условия | Событийный поток стабилен и покрывает нужные данные |
| Выходные условия | Мигрированные витрины согласованы со старым представлением |
| Метрики этапа | Расхождения витрин, freshness, доля прямого чтения Oracle |
| Риски этапа | Неполный поток событий, другая семантика показателей |
| Условие остановки | Новая витрина не воспроизводит согласованные бизнес-данные |
